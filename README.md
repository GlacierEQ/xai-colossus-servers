# Colossus Rack Placement Scenario Planner

An independent portfolio project for testing deterministic placement of declared compute-node power demand into declared rack power capacity.

This repository is **not affiliated with xAI**, does not inspect real servers or network fabrics, and is not evidence of deployment inside Colossus or any production datacenter.

## What is implemented

[`src/rack_planner.py`](src/rack_planner.py) provides a bounded placement model with:

- immutable node and rack scenario records;
- validation for identifiers, finite non-negative power values, capacity, and pre-existing rack usage;
- deterministic first-fit-decreasing placement;
- optional preferred-rack handling with an explicit fallback;
- explicit unplaced-node reasons;
- per-rack used power and remaining headroom;
- no mutation of caller-owned rack objects.

[`tests/test_rack_planner.py`](tests/test_rack_planner.py) verifies placement, preferences, fallback, insufficient capacity, deterministic ordering, pre-existing usage, input immutability, duplicate identifiers, invalid values, and an empty scenario.

## Example

```python
from src.rack_planner import Node, Rack, place

result = place(
    nodes=[
        Node("trainer-a", 8.0, rack_pref="rack-1"),
        Node("trainer-b", 8.0),
        Node("inference-a", 6.0),
    ],
    racks=[
        Rack("rack-1", kw_cap=15.0),
        Rack("rack-2", kw_cap=20.0),
    ],
)

print(result)
```

The returned plan includes every node, the selected rack or an explicit unplaced reason, preference status, and a rack-usage summary.

## Algorithm boundary

```text
validated nodes and racks
        │
        ▼
order nodes by requested kW descending, then node id
        │
        ▼
try valid preferred rack first
        │
        ▼
try remaining racks in caller-declared order
        │
        ├── feasible → record placement and modeled usage
        └── infeasible → record unplaced reason
```

This is a deterministic scenario heuristic. It is not an optimizer and does not claim globally optimal placement.

They are **not** counted as verified components of this public planner. Current blockers include hardcoded topology outputs, synthetic formulas without documented calibration, tracked runtime state, dynamic sibling imports, simulated reset behavior, and tests that sometimes print success without proving the stated integration.

No source is deleted or collapsed. Each experiment must receive its own source-level hardening and receipt before promotion.

## Safety and interpretation

- `kw` and `kw_cap` are caller-supplied scenario values; the planner does not measure power.
- Placement output does not authorize physical installation, switching, or workload movement.
- The model does not account for cooling, phase balance, breaker topology, redundancy, network oversubscription, cable length, weight, floor loading, failure domains, maintenance windows, or service-level objectives.
- Unknown preferred racks and ambiguous duplicate identifiers fail closed.
- Real infrastructure use requires independent electrical, mechanical, network, safety, and operational review.

## Promotion requirements

Before this family can support a broader infrastructure claim, it still needs:

1. typed, versioned schemas for nodes, racks, units, timestamps, and source provenance;
2. additional constraints for cooling, network affinity, failure domains, redundancy, and maintenance state;
3. property tests and comparison against a documented optimization baseline;
4. deterministic scenario fixtures and replay receipts;
5. authenticated adapters for any live inventory or telemetry source;
6. explicit human authority before any external mutation;
7. independent domain review and disclosed benchmark environments.
